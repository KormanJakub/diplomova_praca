# Application Security Audit — 2026-09-14

## Scope and method

This was a static review of the ASP.NET Core backend (`api/nia_api`), its tests, and security-relevant Angular flows (`web`). It did not penetration-test a deployed service or query production data. Findings reflected source behavior on the audit date. A clean package audit alone does not establish application security.

This document is historical. The current implementation is described in [`../CONTEXT.md`](../CONTEXT.md), and the remediation record is [`history/2026-09-15-security-hardening.md`](history/2026-09-15-security-hardening.md).

## 1. Backend behavior and data integrity findings

| Priority | Finding at audit time | Impact | Recommended remediation |
| --- | --- | --- | --- |
| P0 | A guest endpoint could mark any numbered order as paid without Stripe verification. | An unpaid order could appear paid. | Move fulfillment to a signed Stripe webhook and verify amount, currency, order reference, and idempotent state transition. |
| P0 | Stripe checkout accepted price information derived from the browser cart. | A client could attempt to pay a different amount from the order. | Accept only order identity/capability and load the authoritative total on the server. |
| P1 | Registered and guest order creation accepted customization IDs without complete ownership, count, or reuse checks. | Foreign, empty, duplicated, or reused items could enter orders. | Validate every item and claim it atomically before creating the order. |
| P1 | Sequential order IDs were calculated as highest ID + 1. | Concurrent requests could collide. | Use an atomic sequence or internal GUID/ObjectId and retain a unique index. |
| P1 | Password recovery sent/processed incorrect values and lacked a bound one-time proof. | Recovery failed or could become unsafe. | Use a cryptographic, expiring, hashed, atomically consumed reset token. |
| P1 | File copy was not awaited before the stream closed. | Uploaded files could be empty or corrupted. | Await copy completion and test stored bytes. |
| P2 | Revenue KPI included unpaid non-cancelled orders. | Dashboard revenue could be overstated. | Calculate revenue from confirmed payments only. |
| P2 | A customization query returned an unawaited task. | The response could serialize incorrectly. | Await the database query and test JSON output. |
| P2 | Production Angular builds still referenced localhost because no production environment replacement existed. | A deployed browser could call its own machine instead of the API. | Configure a verified production API URL and test the real build. |
| P1 | Frontend login, guards, services, and checkout disagreed about local storage versus cookies. | Login state and API credentials behaved inconsistently. | Use one session strategy across login, logout, guards, and HTTP calls. |

## 2. Security and data-exposure findings

| Priority | Finding at audit time | Impact | Recommended remediation |
| --- | --- | --- | --- |
| P0 | Admin routes lacked effective server-side authorization. | Anonymous users could read or mutate administrative data. | Apply role authorization to the entire controller and validate the role claim on the server. |
| P0 | A public GET seed route deleted catalog and order data. | One request could destroy application data. | Remove seeding from HTTP routing and use an explicit offline development tool. |
| P0 | Profile updates bound a full user object, including role/password fields. | A user could attempt privilege escalation or account manipulation. | Bind an allowlisted DTO and update only editable fields. |
| P0 | User/order endpoints exposed internal user fields or failed to filter by owner. | Password hashes, verification data, or another user's order could leak. | Return response DTOs and include owner identity in database filters. |
| P0 | Guest operations used enumerable sequential IDs without a secret capability. | Orders could be enumerated, viewed, or cancelled by others. | Require a high-entropy, expiring, hashed capability token. |
| P0 | File upload/delete was public and trusted client filenames/types. | Unauthorized mutation, unsafe content, path abuse, and server-detail disclosure were possible. | Require admin role, randomize names, allowlist type/signature/size, and return generic errors. |
| P0 | Credentials and keys existed in tracked configuration or tests. | Published credentials had to be treated as compromised. | Rotate them externally and remove values from the current tree and tests. |
| P1 | Passwords used unsalted fast SHA-256; login/reset lacked sufficient controls. | Offline guessing and credential attacks were easier. | Use a password KDF, cryptographic reset tokens, expiration, one-time use, and rate limits. |
| P1 | A public guest operation could decrement inventory. | Attackers could manipulate stock. | Change stock only during a validated, conditional order transition. |
| P1 | CORS allowed any origin and JWT issuer/audience were not validated. | Browser trust was unnecessarily broad and token boundaries were weak. | Restrict origins and validate issuer, audience, signing key, and UTC expiration. |
| P1 | Browser JavaScript could access the bearer token and trusted a client role value. | XSS could steal sessions and users could forge UI role state. | Use an HttpOnly cookie, CSP, and server-side authorization. Treat guards as UX only. |

## 3. Recommended work order at audit time

1. Stop destructive and authorization-critical P0 paths and rotate credentials.
2. Centralize order pricing, inventory, Stripe session ownership, webhook fulfillment, and state transitions.
3. Repair password hashing and account recovery, add rate limiting, and prevent internal user-model responses.
4. Move toward bounded `Auth`, `Catalog`, `Orders`, `Payments`, `Media`, and `Admin` services with narrow DTOs.
5. Stabilize the frontend on one API environment and one authentication/session model before further UX work.

## 4. Verification recommended at audit time

- Use an isolated MongoDB database and Stripe test environment.
- Test anonymous/user/admin access to every admin route.
- Test foreign-order access, attempted role changes, forged payment completion, unsafe uploads, and concurrent orders.
- Build the backend and production frontend after each coherent change.
- Exercise the complete checkout in staging before release.
